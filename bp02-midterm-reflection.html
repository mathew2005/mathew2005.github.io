Midterm Reflection: What the First Half of CSC 426 Taught Me

November 5, 2026

Halfway through CSC 426, I can see my growth as a software engineer more clearly than I could at the start of the semester. Most of that growth did not come from writing more code. It came from the work around the code: getting a small fix through review, keeping a pull request small enough to merge, and keeping my own record of the work straight. This post is about what went well, what did not, and the one habit I am changing for the second half.

What went well this semester was learning that a fix is not finished when I write it. It is finished when someone else can verify it. My clearest example is the deadline form fix that merged on November 2. I had reported the problem myself: on a narrow screen, the description field could not be clicked because the Add button column stacked over it. The code change was small, a grid class and a label width. But the fix only became real when a classmate tested it in a small window and confirmed it worked, and when the maintainer approved it. Before this course, I judged my work by what I wrote. Now I judge it by whether someone else can read it, test it, and agree it works. That shift changed how I write. I write smaller changes now, because a small change is easier for a reviewer to understand and easier for me to explain. Reviewing taught me the same lesson from the other side. When I reviewed a classmate's pull request that made the deadline textbox resize automatically, I found a missing module and a possible install problem. Reading code I did not write forced me to ask a harder question than I ask of my own work: not what did the author mean, but what will a new contributor actually face when they follow these steps. That is a different kind of attention, and it is the attention I now try to give my own pull requests before I open them.

What did not go as planned was my placeholder credentials pull request, and the reason matters more than the pull request itself. The maintainer asked for changes on October 28: use the example config file that already exists instead of creating a second one. I still have not made that fix. The honest reason is not that the fix is hard. It is that every time I open the pull request, I see more to fix. The existing file still has placeholder values and debug turned on, so it needs cleanup too, and the setup script copies from a folder that does not exist. So the pull request keeps growing in my head, and I keep putting it off. I have learned something uncomfortable about myself from this. I tell myself I am being careful by fixing everything around the problem, but really I am putting it off. If I keep adding work to it, I never have to face the smaller truth: the maintainer asked for one change, and I have not made it. The delay has a cost beyond the open pull request. While it sits open, my contributions file goes stale, my record stops matching reality, and the next person reading it has to guess. The same pattern showed up in my time management this semester. I let small admin work pile up until it felt big, and then I avoided it for the same reason. The pattern is the same in both cases. When a task looks bigger than it is, I delay it, and the delay makes it bigger.

The one habit I want to change for the second half of the semester is scoping my work small before I start it. I will decide what a single pull request is supposed to do, write that down, and stop when it is done. Anything else I notice goes into a separate issue instead of into the pull request I am already working on. I am choosing this because the evidence from the first half is clear. Every pull request I kept small merged. The one pull request I let grow is still open. The cause was in my control. It was not the codebase or the reviewers. It was me adding scope instead of finishing the change the maintainer asked for. This is the right habit to change because the failure was not technical. I treated a pull request as a place to show I had thought of everything, instead of a place to finish one thing well.

My concrete action plan has three parts. First, before I touch code on a new issue, I will write one sentence saying what the pull request will change and one sentence saying what it will not change, and I will put both in the pull request description. Second, when a reviewer asks for a change, I will make only that change and push it within two days, instead of using the review as a reason to rethink the whole file. Third, I will update my contributions file the same day a pull request merges, so the record never goes stale again. I will check myself against this plan every week: if a pull request is open for more than a week without a push from me, I will cut its scope or ask the maintainer whether to split it.

Progress Update: Story Points

So far I have completed 21 story points across four merged pull requests, as recorded in my contributions file: 3 points for PR #141, 8 points for PR #145, 5 points for PR #154, and 5 points for PR #162. That number is what it is because three of those four were small, well-scoped tasks, and the fourth grew. But the number hides the more useful story, which is how badly my estimates matched reality. PR #141 was estimated at 3 points and ran 2 points over, because each round of review added scope: naming the maintainers, documenting both the clone and fork workflows, and merging the development branch back in. At the time that felt like the review process working against me. Looking back, it was the review process working as it should. A contributor guide that only I understand is not a guide. The scope grew because the pull request had to serve people I had not thought about. PR #162 was a small fix that still took weeks from report to merge, because the time went to review and testing, not to writing code. That taught me that my estimates measured the wrong thing. I estimated the coding. The work was the conversation. PR #152, estimated at 2 points and running 1 point over, is not in the completed total at all, because it is still open with changes requested. Its blockers were scope growth and my own delay, not technical difficulty. The learning curve was real but manageable: reading a codebase written over many years by many people is slower than writing a class exercise, and peer review before maintainer review means a pull request is a conversation, not a submission. What the numbers really say is that I am getting better at the parts of software work that do not look like coding, and that my estimates will keep being wrong until I start estimating those parts too.

Outside the resolved issues, my other contributions mattered to the application too. Reporting the unclickable description field myself mattered because nobody can use a form they cannot click, and the fix came from that report. Reviewing a classmate's pull request mattered because a second pair of eyes caught a missing module before it reached users. Updating my contributions file matters because the next person reading it should be able to trust it. What I learned from all of this is that contributing is less about writing code and more about joining a system that keeps code trustworthy, and my job in the second half is to keep my part of that system small, finished, and on time.
