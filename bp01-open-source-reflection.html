Open Source Reflection: Half Semester Contributing to BCSR

October 21, 2026

This semester in CSC 426, I have been contributing to BCSR, a web application used here at Berea College. The Berea College Student Software Development Team maintains it, and students like me pick real issues from the project's tracker: bugs, missing documentation, problems with forms, problems with setup. Working on this project has put me in three roles at the same time. I am a user of open source software, a student learning from it, and a contributor whose code other people review and rely on. Each role has shown me a different side of open source.

As a user, I depend on open source tools every day, often without thinking about it. I manage my code with Git and GitHub. I program in Python. I first learned electronics with Arduino, which later became the subject of my own course. Even my classes run on open source software, since Berea uses Moodle for coursework. The benefit is simple: these tools cost nothing, no company can take them away or change them overnight, and when something breaks, I can look at the code myself. As a student, open source has a different value. Reading a real codebase teaches me things a class exercise cannot, because many people wrote that code over many years, and it holds their good decisions, their shortcuts, and their mistakes. As a contributor, I feel the cost. My work moves at the speed of other people's time. A small issue can take weeks, because a classmate must approve my pull request, the maintainer can ask for changes, and the branch must be updated before anything is merged.

My thesis is simple: open source is a good model for important software, but only when people are clearly responsible for maintaining it. Open code on its own promises nothing. What makes it work is the process around the code: named maintainers, required code review, a security policy, and documentation that a new contributor can follow. There is also an ethical side. When a college or a company depends on a piece of software, that software serves the public, and open development shares the benefit with everyone instead of locking it inside one company. But there is a fairness problem. If important systems depend on unpaid contributors who change every year, the risk falls on the people with the least power to refuse the work, and on the users when the software fails. Open should be the default for this kind of software, but it has to come with real responsibility. Otherwise, it becomes a way to get important work done for free.

BCSR is a small example of both sides. The application is still alive because new students keep joining and picking up issues. No single company could be hired to care for it at this scale. At the same time, its weak points are not code problems, they are process problems. While I was adding example database credentials for new contributors, I found a setup script that points to a folder that does not exist, and an example configuration file from 2020 that did the same job as the file I was adding. The code being open did not cause these problems. They came from setup steps and documentation that nobody owned.

Here is my progress so far. One of my pull requests has been merged: a one-point fix that made the Close button red and the Save button green on the deadline edit form. It finished right at its estimate. Three more pull requests are still open. The contributor guide, which added a security policy and a code owners file, was estimated at three points and is now running two points over. Each round of review added more scope: naming the maintainers, documenting both the clone and fork workflows, and merging the development branch back in. The credentials pull request was estimated at two points and is running one point over, because of the broken setup files I found on the way. I also reported an issue myself, after I found that the description field on the deadline form cannot be clicked when the screen is narrow, and my fix for it is open and approved by a classmate. Teamwork shapes all of this. Our flow is peer review first and maintainer review second, so a pull request is a conversation, not a submission. One of my approved fixes even had its issue reopened the same morning it was approved, which taught me that "done" in open source is never final.

The main lesson so far is that contributing is less about writing code and more about joining a system that keeps code trustworthy. My next step is to get my two open pull requests through maintainer review. I expect the estimates to keep teaching me how much of software work is everything around the code.
